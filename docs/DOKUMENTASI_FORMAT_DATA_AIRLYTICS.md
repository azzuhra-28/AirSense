## 1. SKEMA DATABASE SUPABASE

File: `db_airlytics.sql`. Ada **3 tabel**, semuanya di schema `public`.
Tidak ada foreign key, tidak ada tabel device/lokasi/log/alert.

### 1.1 Tabel `tb_konsentrasi_gas` — Data Sensor Utama (µg/m³ + DHT)

Endpoint REST: `/rest/v1/tb_konsentrasi_gas`

| Kolom | Tipe Data | Nullable | Default | Keterangan |
|---|---|---|---|---|
| `id` | `BIGINT` | NO | `GENERATED BY DEFAULT AS IDENTITY` | **PRIMARY KEY** |
| `created_at` | `TIMESTAMPTZ` | YES | `NOW()` | Waktu insert (UTC) |
| `pm25_ugm3` | `DOUBLE PRECISION` | YES | — | PM2.5 dalam **µg/m³** |
| `pm10_ugm3` | `DOUBLE PRECISION` | YES | — | PM10 dalam **µg/m³** |
| `co_ugm3` | `DOUBLE PRECISION` | YES | — | CO dalam **µg/m³** |
| `no2_ugm3` | `DOUBLE PRECISION` | YES | — | NO₂ dalam **µg/m³** |
| `o3_ugm3` | `DOUBLE PRECISION` | YES | — | O₃ (ozon) dalam **µg/m³** |
| `temperature` | `DOUBLE PRECISION` | YES | — | Suhu **°C** (DHT22) |
| `humidity` | `DOUBLE PRECISION` | YES | — | Kelembapan **%RH** (DHT22) |

### 1.2 Tabel `tb_analog_out` — Nilai ADC Mentah

Endpoint REST: `/rest/v1/tb_analog_out`
Semua kolom nilai = hasil `analogRead()` ADC 12-bit ESP32 → rentang **0–4095**.

| Kolom | Tipe Data | Nullable | Default | Keterangan |
|---|---|---|---|---|
| `id` | `BIGINT` | NO | `GENERATED BY DEFAULT AS IDENTITY` | **PRIMARY KEY** |
| `created_at` | `TIMESTAMPTZ` | YES | `NOW()` | Waktu insert (UTC) |
| `o3_analog` | `DOUBLE PRECISION` | YES | — | ADC MQ131 (pin 32) |
| `pm25_analog` | `DOUBLE PRECISION` | YES | — | ADC GP2Y1010AU0F (pin 35) |
| `pm10_analog` | `DOUBLE PRECISION` | YES | — | ADC GP2Y1010AU0F (pembacaan ke-2) |
| `no2_analog` | `DOUBLE PRECISION` | YES | — | ADC sensor NO₂ (pin 34) |
| `co_analog` | `DOUBLE PRECISION` | YES | — | ADC sensor CO / MiCS-6814 (pin 39) |

### 1.3 Tabel `tb_prediksi_kualitas_udara` — Data ISPU

Endpoint REST: `/rest/v1/tb_prediksi_kualitas_udara`
> Catatan penamaan: tabel ini sekarang diisi firmware dengan **ISPU hasil
> konversi real-time** (bukan hasil forecast ML). Nantinya bisa dipakai juga
> untuk menyimpan output prediksi model.

| Kolom | Tipe Data | Nullable | Default | Keterangan |
|---|---|---|---|---|
| `id` | `BIGINT` | NO | `GENERATED BY DEFAULT AS IDENTITY` | **PRIMARY KEY** |
| `created_at` | `TIMESTAMPTZ` | YES | `NOW()` | Waktu insert (UTC) |
| `pm2_5_ispu` | `DOUBLE PRECISION` | YES | — | ISPU PM2.5 (0–301+) |
| `pm10_ispu` | `DOUBLE PRECISION` | YES | — | ISPU PM10 |
| `co_ispu` | `DOUBLE PRECISION` | YES | — | ISPU CO |
| `no2_ispu` | `DOUBLE PRECISION` | YES | — | ISPU NO₂ |
| `o3_ispu` | `DOUBLE PRECISION` | YES | — | ISPU O₃ |

### 1.4 Ringkasan Aturan Penting

- **Primary key** semua tabel: `id BIGINT IDENTITY` → dummy data **tidak perlu** mengisi `id`.
- **`created_at` tidak perlu diisi** saat POST — otomatis `NOW()` di server.
  (Tapi boleh diisi manual format ISO 8601 UTC, mis. `2026-09-06T01:00:00+00:00`.)
- Semua kolom nilai boleh `null` (tidak ada `NOT NULL`), tapi firmware selalu mengirim semua field.
- Tidak ada relasi antar tabel (tanpa FK) — 3 insert terjadi **paralel/berurutan secara independen**.

## 2. FORMAT PAYLOAD DARI PERANGKAT (ESP32) KE BACKEND

Sumber: `main/senddata.ino`, `main/main.ino`

### 2.1 Protokol & Endpoint

- **Protokol:** HTTP **REST** (bukan MQTT) — `HTTPS POST` via `HTTPClient` + `WiFiClientSecure` (`setInsecure()`).
- **Backend:** Supabase PostgREST API.
  - Host: `https://<SUPABASE_HOST>.supabase.co` *(host asli ada di `main.ino` baris 28)*
- **Endpoint yang dipakai (3 POST per siklus):**

| # | Endpoint | Isi |
|---|---|---|
| 1 | `POST /rest/v1/tb_konsentrasi_gas` | Konsentrasi gas + cuaca |
| 2 | `POST /rest/v1/tb_analog_out` | ADC mentah |
| 3 | `POST /rest/v1/tb_prediksi_kualitas_udara` | ISPU |

- **Header wajib** (semua request):
  ```
  Content-Type: application/json
  apikey: <SUPABASE_ANON_KEY>
  Authorization: Bearer <SUPABASE_ANON_KEY>
  ```
- **Interval pengiriman:** setiap **60 detik** (`sendDataInterval = 1000*60` ms).
- **Urutan:** gas → analog → ISPU. Jika satu gagal (HTTP code di luar 2xx), sisanya **dibatalkan**.
- Respon sukses: **`201 Created`** (body kosong karena firmware tidak kirim header `Prefer: return=representation`).

```json
{

  "pm10_ugm3": 62.30,
  "co_ugm3": 1250.70,
  "no2_ugm3": 41.80,
  "o3_ugm3": 92.50,
  "temperature": 29.60,
  "humidity": 74.50

```

| Field | Tipe | Satuan | Rentang realistis |
|---|---|---|---|
| `pm25_ugm3` | number (float) | µg/m³ | 5 – 150 |
| `pm10_ugm3` | number (float) | µg/m³ | 10 – 250 |
| `co_ugm3` | number (float) | µg/m³ | 200 – 15000 |
| `no2_ugm3` | number (float) | µg/m³ | 5 – 400 |
| `o3_ugm3` | number (float) | µg/m³ | **≥ ~19.6** (clamp min 10 ppb) – 400 |
| `temperature` | number (float) | °C | 22 – 38 · **sentinel error: `-999.0`** |
| `humidity` | number (float) | %RH | 40 – 95 · **sentinel error: `-999.0`** |

> ⚠️ DHT22 gagal baca → firmware mengirim `-999.0` untuk temperature/humidity. Dummy data tidak perlu meniru nilai ini kecuali mau test kasus error.

### 2.5 Rumus Konversi Firmware (untuk generator dummy yang konsisten)

Semua ADC → tegangan: `vout = (adc / 4095.0) * 3.3`

| Polutan | Rumus µg/m³ | Rumus ISPU (rentang x, µg/m³ → ISPU) |
|---|---|---|
| PM2.5 | `218.7*vout − 9.7854` | 0–15.5→0–50 · 15.5–55.4→50–100 · 55.4–150.4→100–200 · 150.4–250.4→200–300 · >250.4→301 |
| PM10 | `288.27*vout − 15.753` | 0–50→0–50 · 50–150→50–100 · 150–350→100–200 · 350–420→200–300 · >420→301 |
| CO | `ppm * (28.01/24.45)*1000`, ppm = `(Rs/7100)^−1.18` | 0–4000→0–50 · 4000–8000→50–100 · 8000–15000→100–200 · 15000–30000→200–300 · >30000→301 |
| NO₂ | `ppm * (46.01/24.45)*1000`, ppm = `vout * 0.05` | 0–80→0–50 · 80–200→50–100 · 200–1130→100–200 · 1130–2260→200–300 · >2260→301 |
| O₃ | `ppb * (48/24.45)`, ppb = `341.38*vout − 126.55` (min 10) | 0–120→0–50 · 120–235→50–100 · 235–400→100–200 · 400–800→200–300 · >800→301 |

Rumus ISPU linear: `ISPU = ((Ia−Ib)/(Xa−Xb)) * (x−Xb) + Ib`

## 3. FORMAT DATA YANG DIKONSUMSI DASHBOARD (FRONTEND)

> ⚠️ Dashboard Next.js **belum dibuat** — tidak ada kode fetch yang ditemukan.
> Bagian ini adalah **kontrak format** yang akan dipakai frontend
> (bentuk response standar Supabase/PostgREST). Buat dummy data sesuai bentuk ini.

### 3.1 Bentuk Response Umum (Supabase JS Client / PostgREST)

- `GET`/`select` mengembalikan **JSON array of objects** (bukan object tunggal), satu object = 1 row tabel.
- Kolom `id` dan `created_at` **selalu ikut** dalam response (walaupun tidak dikirim saat insert).
- `created_at` berformat ISO 8601 UTC dengan mikrodetik, contoh: `2026-09-06T01:00:00.123456+00:00`.

### 3.2 TypeScript Interfaces (usulan kontrak)

```typescript
// === Row mentah dari Supabase ===

export interface KonsentrasiGas {
  id: number;
  created_at: string;          // ISO 8601 UTC
  pm25_ugm3: number | null;    // µg/m³
  pm10_ugm3: number | null;    // µg/m³
  co_ugm3: number | null;      // µg/m³
  no2_ugm3: number | null;     // µg/m³
  o3_ugm3: number | null;      // µg/m³
  temperature: number | null;  // °C
  humidity: number | null;     // %RH
}

export interface AnalogOut {
  id: number;
  created_at: string;
  o3_analog: number | null;    // 0-4095
  pm25_analog: number | null;  // 0-4095
  pm10_analog: number | null;  // 0-4095
  no2_analog: number | null;   // 0-4095
  co_analog: number | null;    // 0-4095
}

export interface PrediksiKualitasUdara {
  id: number;
  created_at: string;
  pm2_5_ispu: number | null;
  pm10_ispu: number | null;
  co_ispu: number | null;
  no2_ispu: number | null;
  o3_ispu: number | null;
}
```

### 3.3 Pola Query yang Akan Dipakai (definisi format per kebutuhan UI)

**a) Kondisi real-time** — 1 row terbaru:

```typescript
const { data } = await supabase
  .from('tb_konsentrasi_gas')
  .select('*')
  .order('created_at', { ascending: false })
  .limit(1);
// Bentuk yang diharapkan frontend: KonsentrasiGas[] (array berisi 1 object)
```

**b) Data historis** — rentang waktu (chart):

```typescript
const { data } = await supabase
  .from('tb_konsentrasi_gas')
  .select('created_at, pm25_ugm3, pm10_ugm3, co_ugm3, no2_ugm3, o3_ugm3, temperature, humidity')
  .gte('created_at', '2026-09-06T00:00:00+00:00')   // ISO 8601
  .lte('created_at', '2026-09-06T23:59:59+00:00')
  .order('created_at', { ascending: true });
// Bentuk: KonsentrasiGas[] (array, urut waktu naik)
```

**c) Hasil forecast/prediksi** — tabel ISPU (dan nanti tabel prediksi ML):

```typescript
const { data } = await supabase
  .from('tb_prediksi_kualitas_udara')
  .select('*')
  .order('created_at', { ascending: false })
  .limit(24);
// Bentuk: PrediksiKualitasUdara[]
```

## 4. FORMAT OUTPUT MODEL ML

> ⚠️ Kode ML (XGBoost / Random Forest) **belum ada di codebase** — tidak ditemukan
> script/notebook terkait. Bagian ini mendokumentasikan **kontrak input/output
> yang disarankan**, konsisten dengan skema DB & perhitungan ISPU firmware.

### 4.1 Model Forecasting (XGBoost) — prediksi konsentrasi/ISPU ke depan

> ✅ **Spesifikasi pasti dari laporan Yusuf (bab 3.2.5 & 4.7.6):**
> - **Target**: PM2.5, PM10, dan **CO** — masing-masing model terpisah
> - **Horizon**: **60 menit** ke depan
> - **Hyperparameter**: `n_estimators=300, max_depth=6, learning_rate=0.05,
>   subsample=0.8, colsample_bytree=0.8, reg_alpha=0.1, reg_lambda=1.0`
> - **Fitur**: 5 polutan + suhu + kelembapan + waktu + **lag 1 menit** (prediktor
>   terkuat, dari analisis PACF) — data per-menit, 30 hari ke belakang
> - **Preprocessing**: pagination 1000 baris/batch, `dropna()`, outlier IQR
> - **Evaluasi**: MAPE PM2.5 **7.50%**, PM10 **9.00%**, CO **6.36%** (unggul LightGBM & Prophet)
> - **Output di dashboard**: area chart **ISPU per polutan, 60 titik interval 1 menit**
>   + kartu ringkasan (kategori ISPU, ISPU total, polutan dominan)

**INPUT** (time series historis, diambil dari `tb_konsentrasi_gas`):

```json
[
  {
    "created_at": "2026-09-06T00:00:00+00:00",
    "pm25_ugm3": 28.43,
    "pm10_ugm3": 62.30,
    "co_ugm3": 1250.70,
    "no2_ugm3": 41.80,
    "o3_ugm3": 92.50,
    "temperature": 29.60,
    "humidity": 74.50
  }
]
```

+ fitur turunan yang lazim dibuat: `hour` (0–23), `day_of_week` (0–6), `is_weekend` (0/1), lag features (nilai t−1, t−24).

**OUTPUT** (forecast, misal 24 jam ke depan — kontrak yang disarankan):

```json
{
  "model": "xgboost",
  "target": "pm25_ugm3",
  "horizon_hours": 24,
  "generated_at": "2026-09-06T08:00:00+00:00",
  "predictions": [
    {
      "timestamp": "2026-09-06T09:00:00+00:00",
      "pm25_ugm3_pred": 30.12,
      "pm25_ispu_pred": 69.20,
      "category": "Sedang"
    }
  ]
}
```

| Field output | Tipe | Keterangan |
|---|---|---|
| `timestamp` | string ISO 8601 | Waktu prediksi |
| `*_pred` | float | Nilai konsentrasi hasil prediksi |
| `*_ispu_pred` | float | ISPU hasil konversi prediksi |
| `category` | string | `Baik` / `Sedang` / `Tidak Sehat` / `Sangat Tidak Sehat` / `Berbahaya` |

### 4.2 Model Klasifikasi (Random Forest) — kategori kualitas udara

> ✅ **Spesifikasi pasti dari laporan Yusuf (bab 4.7.7):**
> - **Peran**: *robustness layer* — menstabilkan kategori ISPU agar tidak
>   flickering saat sensor fluktuatif di ambang kategori (boundary smoothing)
> - **Input**: 5 polutan mentah (µg/m³), **tanpa feature engineering**
> - **Hyperparameter**: `n_estimators=500, max_depth=14, min_samples_leaf=2`
> - **Target**: kategori ISPU (5 kelas)
> - **Pelatihan**: split 75:25 stratified, synthetic data multivariate normal
>   hanya di data latih, **Gaussian noise injection 10%**
> - **Hasil drift test**: akurasi 82.3% & F1-Macro 68.1% pada noise 10%;
>   paling resisten di noise 25% (69.3%, unggul XGBoost/LightGBM/Breakpoint rule)

**INPUT**: 1 baris pengukuran (sama seperti 4.1, tanpa `created_at`).

**OUTPUT** (kontrak yang disarankan):

```json
{
  "model": "random_forest",
  "input_source": "tb_konsentrasi_gas",
  "predicted_at": "2026-09-06T08:00:00+00:00",
  "prediction": {
    "category": "Sedang",
    "class_index": 1,
    "confidence": 0.87,
    "probabilities": {
      "Baik": 0.08,
      "Sedang": 0.87,
      "Tidak Sehat": 0.05,
      "Sangat Tidak Sehat": 0.00,
      "Berbahaya": 0.00
    }
  }
}
```

| Field | Tipe | Keterangan |
|---|---|---|
| `category` | string | Label kelas ISPU |
| `class_index` | int | 0–4 (urut sesuai tabel kategori) |
| `confidence` | float 0–1 | Probabilitas kelas tertinggi |
| `probabilities` | object | Distribusi probabilitas semua kelas |

## Lampiran B: Temuan/discrepancy yang perlu diputuskan (khusus Anggota 1)

1. **Kontrak data di jobdesk menyebut `device_id` & `location`**, tapi skema DB
   aktual (`db_airlytics.sql`) **tidak punya** kolom itu. Keputusan: tambahkan
   kolom, atau konfirmasi bahwa AirSense v2 = 1 node statis (cukup tanpa kolom).
   > Catatan: laporan Yusuf menyebut 3 titik lokasi (Ngagel, Rungkut, Margomulyo)
   > tapi perangkat dipindah-pindah — data riil tidak punya kolom lokasi.
2. **Nama tabel di desain laporan** (bab 3.2.3) disebut `sensor_data` & `forecast`,
   tapi **implementasi aktual** = `tb_konsentrasi_gas`, `tb_analog_out`,
   `tb_prediksi_kualitas_udara`. Dokumentasi ini mengikuti yang aktual.
3. **Tabel agregasi** (per jam/hari, Gambar 3.4 laporan) belum ada di
   `db_airlytics.sql` — di laporan dibuat via Edge Functions + cron job + RPC.
   Perlu dibuat ulang kalau dashboard akan menampilkan chart berbasis agregat.
   Contoh dummy-nya sudah disiapkan: `dummy_data/output/dummy_agregasi_per_jam.csv`.
4. **Protokol**: bab desain laporan menyebut MQTT, tapi **implementasi & firmware
   aktual = HTTPS REST POST ke Supabase** (sesuai bab 4.6.2.1). Ikuti yang aktual.
5. **Dashboard Yusuf = React + Recharts + Supabase Realtime** (bukan Next.js).
   Anggota 3 bebas pakai Next.js, tapi pola konsumsi data (Supabase client)
   tetap seperti di bagian 3.
6. **Forecast format di dashboard Yusuf**: 60 titik × interval 1 menit, per
   polutan PM2.5/PM10/CO dalam bentuk **ISPU** + kartu ringkasan (kategori,
   ISPU total, polutan dominan). Contoh: `dummy_data/output/dummy_forecast_60menit.json`.
